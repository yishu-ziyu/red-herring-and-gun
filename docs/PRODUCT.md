# 红鲱鱼与枪 · 产品定义

本文件定义产品应该是什么样。代码还没做到的地方，列在最后一节「现在的状态」。决定的来由见 `docs/DECISIONS.md`。

## 产品是什么

用户听到一句说法，拿不准真假。用户把这句话、一张截图或一个链接交给产品。产品把说法拆成几截，分别去找公开证据，然后告诉用户：哪一截成立、哪一截有问题、哪一截还查不清，每个判断凭什么，出处在哪里，能点开原文。

追出处是证据工作的一部分：这句话从哪来，是不是一手，转载时有没有被添油加醋。

用户是普通人。他们没有专业背景，不会配置模型，也不会为查一句话注册账号。

## 两条底线

1. **展示证据和判断，不展示 AI 的执行过程。** 用户要检查的是「这个判断为什么成立」：原句被拆成了什么，每一截找到了哪些证据，哪些支持、哪些反驳、哪些只是相关、还缺什么，结论因此如何得出。模型名、工具调用、执行日志、内部用语都不出现在界面上。
2. **复杂调查，简单理解。** 严谨不等于难用。好懂、低摩擦、好看是验收的一部分，不是上线后再补的装饰。视觉验收要写清「应该长什么样」，不能只写禁令，因为只有禁令的设计最后会变成一张灰纸。

## 用户走的路

只有一条主路径。其他能力挂在这条路上，不另开入口。

```text
输入一句话 / 截图 / 链接
  → 拆题：这句话被拆成哪几截，分别要查什么
  → 证据：每一截的支持、反驳、仅相关、尚缺
  → 冲突和缺口：证据打架时说明争点；缺什么照实写
  → 判断：结论第一句直接回答原句
  → 出处：任何一个关键判断都能点到原文
```

三件事必须让用户能检查：

| 检查什么 | 用户看到什么 |
|---|---|
| 拆题 | 原句被拆成了哪几截，和原句放在一起对照，看有没有改变原意 |
| 证据 | 每一截的证据分别是支持、反驳、仅相关还是尚缺，每条证据都能点开出处。没有来源就写没有来源，不拿相关材料凑数 |
| 判断 | 结论为什么成立，冲突在哪里，还不能推出什么 |

## 判断怎么表达

### 每一截的标签

每一截下面显示一个标签，后面跟一句理由。标签单独出现最容易被误读，所以理由不能省。

| 标签 | 什么时候用 | 颜色 |
|---|---|---|
| 属实 | 公开资料证实了 | 绿 |
| 基本属实 | 主要内容对，细节有出入 | 绿 |
| 部分属实 | 一部分对，一部分错 | 黄 |
| 夸大了 | 有一部分道理，但说得太重 | 黄 |
| 不属实 | 公开资料说的是相反的事 | 红 |
| 还查不清 | 能查，查了，但公开资料不够下结论 | 灰 |
| 无法核对 | 按性质现在查不了：还没发生的事，没有公开记录的私下的事 | 灰 |
| 说法不一 | 权威来源之间互相矛盾 | 灰 |
| 是观点，不分对错 | 这是价值判断，不是事实 | 灰 |

颜色只做辅助，不能单独表示判断。

没有依据可查的预测用「无法核对」，不用「是观点」，因为预测是关于事实的说法，只是事实还没发生。如果预测有现在就能核对的依据，例如官方文件或已发布的权威预测，就去查那个依据。

整句的标签由各截的标签推出，用同一套 9 个标签。主要说法错了，整句就是「不属实」；只有背景细节错，整句是「基本属实」；对错混在一起，整句是「部分属实」。规则在代码里：`apps/server/src/domain/verdict.ts`。

### 结论第一句

结论第一句 = 整句标签 + 一句理由。理由说明各截怎么合成整句判断，不重复某一截的理由，具体证据留在每一截下面。例如：

> **不属实。** 主要说法「隔夜菜会致癌」被权威辟谣反驳；「等于吃毒药」只在室温放久时有一点道理，说得太重。

标签由代码按规则决定，保证结论不会和判断矛盾。理由由模型写，只能使用这次找到的证据，不能凭记忆补充事实。

### 证据

- 每条证据显示：原文里的那句话、来源、来源的发布日期。谣言常常是旧新闻被重新转发，所以日期必须看得见。
- 点证据能打开原网页，并跳到那一句。
- 以后显示每一截有几家独立来源。来源单薄时照实告诉用户：摊开依据也包括摊开弱点。这一项要等同文转载能合并成一家以后再做，否则数字会误导。

### 写法

- 一句只说一件事。抽象的判断后面马上跟一条具体出处。
- 半真半假时，点名哪一截成立。查不清就说查不清。没搜到不等于假。
- 失败要明说。搜索失败、超时、来源打不开，都显示为状态，不能用一段流畅的话糊弄过去。
- 只回答原句。不给「转不转」「先别转发」这类行动建议。

## 默认体验

这些规则来自 2026-09-17 的用户确认。

- 用户不用先选模式，提交就开始查。
- 优先查主要主张和回答它所需的依据。没有查到或没进本轮的部分，必须明确说没查，不能让人以为全文都核过了。
- 重要发现可以提前显示，但不能冒充最终结论。
- 查完可以追问。追问留在同一份调查里，保留之前每一轮的问题、结果、出处和核查日期。追问失败或被停止，不覆盖原来的结果。
- 换一个问题，就开一份新调查。
- 打开历史记录只是读取，显示原来的日期，不重新调查。
- 用户再次输入和以前完全相同的文字时，让用户自己选择：打开以前的调查，还是重新调查。只要加了链接或图片，或者人物、日期变了，就当成新的说法，不沿用以前的结论。
- 保存失败要让用户看见。

## 输入

- 文字、截图、链接三种。
- 不收视频。只截几帧画面、听不到声音，用户会误以为视频已经查过了。

## 结果页上能做的事

结论下面直接显示依据。操作只有三个：

- **追问**：一个输入框，接着问这份调查。
- **分享**：生成一个别人能打开的链接，也能复制文字简报。不需要登录。分享只带所分享的那一轮结果，可以撤销。
- **新调查**：查另一句话。

历史记录存在用户自己的浏览器里。

## 证据冲突时

证据打架时，可以请第二个模型对争点提出质疑，再定向补查。判断可以根据新证据改变。意见分歧本身不是证据，不能用「大家都同意」代替证据。这个阶段是否保留，要看补查阶段的对比测试（#145）。

## 界面

- 这是核查产品，不要做成 AI 运维面板。
- 第一屏要回答三件事：这句话站不站得住，凭什么，来源在哪。
- 完成后按论证的顺序读：判断 → 解释 → 依据。
- 调查中按实际进度一步步出现，不把还没开始的部分提前铺开。
- 衬线字体给判断句、原句和摘录，无衬线字体给界面。动效要尊重用户「减少动态效果」的系统设置。
- 产品可以有拟人化的视觉角色，但它只是这次调查的视觉形象，不能出现在执行过程里，不能扮演判断者，不能代表证据。

## 明确不做

- 不是「先别转发」公益广告，不是「转不转」顾问，不是措辞教练。
- 不展示虚构的角色对话或 AI 运维面板。
- 不做没有边界的自主执行。补查要有次数上限、引用约束、停止条件和失败状态。
- 不是聊天。追问问的还是这份材料。
- 不要求用户登录，不保存用户的邮箱。
- 不在用户之间共享调查内容。以后如果要做「查过的说法给所有人复用」，至少要满足：只收公共说法；带核查日期，新结果追加、不覆盖；命中后仍然联网搜新证据。
