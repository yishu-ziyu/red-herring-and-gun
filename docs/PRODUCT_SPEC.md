# 红鲱鱼与枪 · 产品说明书

> 本文档是产品的**唯一真相源**。所有关于"产品为什么这样设计、功能怎么实现、对象是什么"的讨论，都沉淀在本文档里。
> 之后每产生一个新的产品问题或结论，都追加到对应章节，不另起炉灶。

## 一、产品是什么

"红鲱鱼与枪"是一个 AI 信息核查 Agent。用户提交一条疑似传言、截图转写、链接或网页材料，系统用多 Agent 流程完成立案、命题拆解、证据搜索、交叉验证和报告收束，输出可信度评分与证据链。

一句话定位：

> 先别转发，先看证据链。

它不是"搜索总结工具"，而是把一条说法拆成可核查判断，再按证据许可给出 can say / cannot say。

## 二、产品面对的对象：谣言的结构特性

产品的设计不是自嗨，而是从**对象（谣言）的固有特性**倒逼出来的。

**谣言不是"全错"的东西，它是"半真半假"的东西。** 它往往把真实的部分和错误的部分缝在一起。正因为如此，如果不拆、把它当整体去判断，只能得到"半真半假"这个模糊结论——而"半真半假"恰恰是谣言最擅长的伪装，它靠这个存活。

**这个特性决定了两个核心设计结论：**

1. **必须拆分**（见第三章）
2. **必须能区分"能说什么"和"不能推出什么"**（见第四章）

## 三、核心任务：命题拆解

### 为什么必须拆分

最初以为"因为谣言很长所以必须拆"，但这不是根因。**"长"不是必须拆的理由**——一句很短的话也可能是混合命题，一句很长的话也可能只有一个核心判断。

真正的根因是：**一条消息里往往藏着多个独立的可核查判断，而它们各自需要不同的证据、不同强度、甚至不同的真假结论。**

例子：

- "这个药能治失眠，而且已经获得国家批准" —— 前半句是"药效"（医学判断），后半句是"是否获批"（事实判断）。两个根本不是一回事，一个可能真、一个可能假，必须分开查。
- "某某公司即将倒闭，内部员工已经离职潮" —— "公司倒闭"和"员工离职潮"是两个断言。人可能走了，但公司未必倒。

### 不拆的后果

1. **证据串味**：一个子命题的强证据，会被拿来糊弄另一个子命题的判断。
2. **结论骑墙**：没法给一句话干净的真假，只能给"部分可信"，说不清哪部分真、哪部分假。

### 拆分的本质

拆分就是把谣言"真与假交织"的缝线剪开，让真实的部分单独验、错误的部分单独验、夸大/偷换的部分单独验。这样真、假、夸大各归其位，谣言赖以存在的"以假乱真"的掩护就破了。

### 拆分方法论的出处（2026-08-05 检索确认）

"把一个主张拆成可独立核查的原子命题"是事实核查领域的标准做法，不是我们的自创。证据来源（全部一手，arXiv / ACL Anthology）：

- **《A Closer Look at Claim Decomposition》**（Wanner et al., Johns Hopkins, *SEM 2024）。这是拆分本身的直接出处。它把拆解产物统一叫 subclaim，并注明 "atomic fact" 与 "atomic proposition" 是近义概念。它的理论根基追溯到 **Bertrand Russell 的逻辑原子主义 + neo-Davidsonian 语义学**：原子事实是个体性质或个体间关系，拆解目标是把句子拆成"每个 subclaim 指称一个个体性质或两个个体之间的关系"的最小单元。它还提出两处关键取舍：**不要求 subclaim 相互独立**，只要求"每个 subclaim 都被原句声称"；提出 **DecompScore** 度量拆解质量（用"原句本身"做验证上下文，测出拆解产出的 subclaim 有多少被原句支持）。它最重要的警示是：**FActScore 这类指标把拆解误差算到生成模型头上**，必须显式区分"拆解错误"与"生成错误"。
- **《Distill and Align Decomposition for Enhanced Claim Verification》**（JPMorgan AI Research, EACL 2026）。它把 "decompose-then-verify" 定性为当前主流框架：句子 → 拆解器 → 子命题集合 → 检索 → 证据 → 验证器 → 聚合。它明确拆解器引入三类噪声：**over-fragmentation（过度碎片化）、context loss（上下文丢失）、insufficient decontextualisation（去语境化不足）**，都会污染下游检索和验证。它用 GRPO 联合优化"拆解质量"与"验证器对齐"，并给出四步顺序推理（主张检测 → 去语境化 → 关系识别 → 主张抽取），其中"去语境化"保证子命题自足、可单独检索。
- **《LoCal: Logical and Causal Fact-Checking with LLM-Based Multi-Agents》**（CVPR 2025）。用专门 decomposing agent 把复杂 claim 拆成"事实验证任务 + 问答任务"两类子任务，再交给两类推理 agent；用两个评估 agent 检查子任务能否**逻辑还原回原始 claim** 并经受反事实冲击，直到双通过或达最大迭代次数才出结论。可解释性来自"结构化 solution + 评估过程描述"。

**对"为什么拆"的独立加强**：上述论文讲的拆分主要是为了"验证性能"（长文事实性核查）。我们"因谣言半真半假特性必须拆以保证可审计性"的论证，是产品层自研推导，与业界标准的动机不同但方向一致——这是需要单独标注的边界：**方法论出处（怎么拆）来自业界，产品动机（为什么这么拆）是自研。**

### 与业界拆解器的差距分析（2026-08-05）

对照三篇论文，当前实现的关键差距（按"成本低 → 收益高"排序）：

1. **缺"原子命题"的判定标准**。业界（A Closer Look）有明确定义：原子命题 = 个体性质或个体间关系，且"不要求独立、只要求被原句声称"。我们 RumorDetector 的 prompt 只有一句"先拆出可核查的原子命题"，未定义判定标准、粒度、数量上限、回溯约束。**下一步可借鉴**：把"每个原子命题必须能被原句自证"写进 prompt，成本最低。
2. **缺"去语境化"步骤**。DAD 明确去语境化是拆解质量核心（子命题自足、代词消解、实体指明），否则检索不到。我们直接拆，没做自足化。由于下游要拿 claimAtoms 去核查，**不自足的子命题会查不到**，这是高价值缺口。
3. **缺"拆解质量校验闸门"**。三篇都强调拆解会引入噪声（过度碎片化 / 上下文丢失 / 引入未声称信息）。我们的 changelog 已承认"没有一道闸核对拆解忠不忠实、完不完整"。**最可落地**：借鉴 DecompScore，用"原句自证"过滤掉不被原句支持的 subclaim。
4. **缺"与下游对齐"**。DAD 用 RL 对齐，LoCal 用评估器闭环迭代。我们单向原样喂给 FactChecker/SourceValidator。这是演进方向，重要性低于前三项，不必现在做 RL。

**历史策略（已废弃，2026-08-06 前）**：搜索只锚定原始整句 claim，原子不进检索。拆错不易污染搜索，但原子无法驱动取证，与学界 decompose-then-verify 不一致。

### 检索策略（2026-08-06 起 · 对齐学界）

采用 **先拆再验（decompose-then-verify）** 的取证方式：

```text
原句
  → 拆成原子，并丢掉原句没说过的
  → 可核查原子：每个原子各自检索一轮（上限 6 条原子）
  → 不可核查（立场/价值等）：不发起真假向检索，只标注
  → 每条用「自己的检索结果」辅助判定
  → 报告按条写出结论，并绑上该条相关来源
```

| 原则 | 含义 |
|------|------|
| 原子驱动检索 | 可核查声称是搜索 query，不是装饰 |
| 按条绑证据 | 用户展开某条定罪时，看到的主要是为该条取到的材料 |
| 无证据 ≠ 假 | 定向检索无结果 → 「未能证实 / 待补证」，不自动判假 |
| 拆错会伤检索 | 因此必须保留原句自证：进搜索前原子须被原句支持 |

**本阶段明确不做**：整句兜底二次搜、相似 query 合并、结果缓存、动态上限（见工单后续）。

### 并行检索提供方（2026-08-06 实测）

生产路径一次原子检索会并行调用（有 key 才真请求）：

| 提供方 | 接口现状 | 备注 |
|--------|----------|------|
| 360 | **仅** `/v2/mwebsearch` | 已下线超时的 `/v1/search/aisearch`；mweb 带 `trusted_sources` / `exclude_aigc` |
| Tavily | `POST api.tavily.com/search` | 文档仍为此端点，实测可用 |
| Exa | `POST api.exa.ai/search` | 2026 文档推荐 `contents.highlights`，已按此取摘要 |
| Metaso | `POST metaso.cn/api/v1/search` | 返回 `webpages`，实测可用（注意余额） |
| AnySearch | MCP `tools/call` search | 可用但结果偏少 |

任一源失败不阻断整次并行（`Promise.allSettled`）；全部失败才报搜索失败。

### 「少捞垃圾」聊清楚（产品边界）

检索**不能保证**结果权威。当前分层是：

```text
1. 多源宽召回（每可核查原子一轮）
   · Tavily / Exa / Metaso / AnySearch / 360 mweb 并行；失败不阻断
   · 360 mweb：trusted_sources + exclude_aigc（仅该源）

2. 筛选漏斗 v1（确定性，进 FactChecker 前）
   · S1 硬过滤：无 http(s) / 无法 parse / 标题与摘要皆空 / denylist 短链域
   · S2 跨源去重：规范化 URL（去 utm/hash）；否则 域名+标题
   · S3 可用度打分 + 每原子 top-5（域名启发式可信度 + 摘要质量 + 源内次序）
   · 可观测：bundle.filterMeta（before → afterFilter → afterDedupe → afterTopK）
   · 「低」可信只降权，不因「低」直接删除（避免误杀线索）

3. 读材料时（FactChecker / SourceValidator）
   · 偏好权威、可疑进 questionable、禁止编造 URL

4. 分数与边界
   · 信源差 → 公式降分；无据 → 未能证实 / cannot say
```

实现：`mvp/server/src/lib/retrievalFilter.ts`；决策稿 `mvp/docs/superpowers/specs/2026-08-06-retrieval-quality-decision.md`。

**不要对外说「我们只搜好东西」。**  
正确说法：**我们尽量少把不可追溯噪声送进证据链，并对差来源降权、暴露给用户。**

### 验收句（用户将看到）

1. **When** 一条说法被拆成多条可核查声称且系统跑完，**Then** 报告「逐命题定罪」里每条可展开，并尽量展示**与该条相关的来源链接/摘要**（而非所有条共用说不清归属的一堆链接）。  
2. **When** 某条可核查声称定向检索没有任何来源，**Then** 该条表现为未能补证/待补证类信息，**不得**仅因「没搜到」就写成「假」。  
3. **When** 某条被标为立场/价值等不可用真假硬判，**Then** 不为该条发起「证真证伪」向的原子检索展示。

实现工单：`mvp/docs/superpowers/specs/2026-08-06-per-atom-retrieval.md`。

## 四、功能实现方式：一大段确定性逻辑 + 关键节点挂 LLM

整个产品的核心不是"AI 很聪明"，而是**每一步都有人管、有地方兜底**。拆开看，它是"确定性代码 + 几个关键节点上挂 LLM"。

**消息进入系统后的完整链路：**

1. **判命题类型**（确定性正则，见第五章）
2. **生成执行图 DAG**（`buildAdaptiveExecutionPlan()` 按类型拼节点和边，再拓扑排序决定谁先谁后、谁可并行）
3. **裁剪每个 Agent 的输入**（`buildAgentInput()`，每个 Agent 只收到它职责所需的材料，不塞全量）
4. **LLM 只做命题性判断，分数和边界由公式算**（见第六章）
5. **报告收束前过一道证据边界闸门**（见第七章）

**模型真正做事的节点：**

- RumorDetector：拆原子命题、识别谣言特征（需要语义理解）
- FactChecker：判断哪些是支持、哪些是反驳、哪些未解决
- SourceValidator：评估来源可靠性与可追溯性
- ReportComposer：合成报告

**模型不做的事：**

- 判类型（正则）
- 排序（拓扑）
- 打分（公式）
- 划边界（契约）

**为什么这么分层：** 模型擅长模糊判断，不擅长核算和边界。核算交给公式，边界交给契约。拆开之后，输出可复现、可审查、可兜底。

## 五、命题类型判断：目前是固定规则

### 当前实现

第一步判断命题类型，目前**不是模型做的，是几行正则（固定规则）**：

```typescript
function detectClaimType(claim: string): ExecutionDagClaimType {
  if (/(什么是|定义|概念|如何理解|是什么意思)/.test(claim)) return "concept";
  if (/(导致|造成|引发|因为|由于|归因|致癌|会让|使得|影响)/.test(claim)) return "causal";
  if (/(网传|称|据说|爆料|发生|发布|宣布|报道)/.test(claim)) return "event";
  return "mixed";
}
```

**正则是"按规则找字"的写法**，不读语义，只认字面。跑一万次结果一样。

### 为什么用正则

确定、可复现、零成本、零幻觉。在"先把流程跑通"的阶段，确定性比聪明更重要。

### 它的局限（必须诚实承认）

1. **不懂语义，只认词面**：会被"字面没命中但实际是同类"的句子骗过，也会被"字面命中但其实是另一回事"的句子误判。
2. **顺序是硬编码的**：先查概念、再查因果、再查事件，存在优先级 bug 隐患。
3. **用关键词代替了"判断"**：一个真正要判类型的系统应读懂句意，而不是"看到'导致'就喊因果"。

**结论：它是占位符，不是终局方案。** 正确做法是让 Planner（或 RumorDetector）用模型读语义判类型，还能对"一句话里多个子断言"分别路由。DAG 里的 `planner` 节点本想做这件事，但目前被跳过了（实际起作用的还是正则）。

## 六、可信度评分：公式算的，不是模型拍的

最终 0-100 的可信度分数，不是模型算的，是 `credibilityScore.ts` 里一个确定性公式，把五类信号加权聚合：

| 分量 | 来源 | 作用 |
| --- | --- | --- |
| 事实核查信号 | FactChecker | 判断核心事实是否成立 |
| 搜索证据信号 | 外部搜索 | 检查外部证据方向和质量 |
| 信源可靠性 | SourceValidator | 评估来源可信度 |
| 谣言严重度惩罚 | RumorDetector | 识别情绪煽动、匿名信源、绝对化表述等风险 |
| 缺失来源惩罚 | SourceValidator | 处理关键证据缺口 |

分档：80-100 高度可信 / 60-79 基本可信 / 40-59 存疑 / 20-39 低可信 / 0-19 高度可疑。

模型给方向，公式给分数，这样分数可复现、可解释、可追责。

## 七、证据边界：can say / cannot say

ReportComposer 的 prompt 里写死一条规则：**只能基于前序 Agent 已经输出的内容和搜索摘要，不能自己"想起"任何事实。** 它必须输出 `canSay`（证据允许说的）和 `cannotSay`（证据不允许说的）两个列表。

例子（"隔夜菜致癌"）：它只能说"正常储存下含量远低于安全限量"，而"不能说危险"——因为没找到实测数据。

正是这种"知道自己不能说什么"的克制，构成核查产品的信任来源。

## 八、失败的兜底

失败是 Agent 产品的常态，不是异常。设计原则是**失败要显式化，但不能让用户看到裸奔**。

1. **失败显式化**：搜索失败、模型超时、来源不可达，都显示为状态，而不是补写解释糊弄过去。
2. **可继续策略**：声明哪些是"可选/并行 Agent"（替代解释、反证评分），它们失败可继续走主线不阻断收束；核心 Agent 失败则阻断。
3. **确定性兜底**：ReportComposer 超时走确定性 fallback 公式，保证用户至少拿到结构完整的报告，不撒谎、不空白、不无限 loading。

## 九、多 Agent 的成本控制

- **输入瘦身**：每个 Agent 只收到职责所需的裁剪材料，token 上限不同。
- **检索**：可核查原子各自检索（上限 6），结果按条注入 FactChecker；聚合来源仍可给 SourceValidator 做总览。后续可用合并 query / 缓存压成本。
- **成熟度分级**：不同 Agent 配置不同 reasoning effort，不平均烧。
