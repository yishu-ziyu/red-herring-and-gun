## 一、产品是什么

"红鲱鱼与枪"是一个 AI 信息核查 Agent。用户提交一条疑似传言、截图转写、链接或网页材料，系统用多 Agent 流程完成立案、命题拆解、证据搜索、交叉验证和报告收束，输出可信度评分与证据链。

一句话定位：

> 先别转发，先看证据链。

它不是"搜索总结工具"，而是把一条说法拆成可核查判断，再按证据许可给出 can say / cannot say。

## 二、产品面对的对象：谣言的结构特性

产品的设计不是自嗨，而是从**对象（谣言）的固有特性**倒逼出来的。

**谣言不是"全错"的东西，它是"半真半假"的东西。** 它往往把真实的部分和错误的部分缝在一起。正因为如此，如果不拆、把它当整体去判断，只能得到"半真半假"这个模糊结论——而"半真半假"恰恰是谣言最擅长的伪装，它靠这个存活。

**这个特性决定了两个核心设计结论：**

1. **必须拆分**（见第三章）
2. **必须能区分"能说什么"和"不能推出什么"**（见第四章）

## 三、核心任务：命题拆解

### 为什么必须拆分

最初以为"因为谣言很长所以必须拆"，但这不是根因。**"长"不是必须拆的理由**——一句很短的话也可能是混合命题，一句很长的话也可能只有一个核心判断。

真正的根因是：**一条消息里往往藏着多个独立的可核查判断，而它们各自需要不同的证据、不同强度、甚至不同的真假结论。**

例子：

- "这个药能治失眠，而且已经获得国家批准" —— 前半句是"药效"（医学判断），后半句是"是否获批"（事实判断）。两个根本不是一回事，一个可能真、一个可能假，必须分开查。
- "某某公司即将倒闭，内部员工已经离职潮" —— "公司倒闭"和"员工离职潮"是两个断言。人可能走了，但公司未必倒。

### 不拆的后果

1. **证据串味**：一个子命题的强证据，会被拿来糊弄另一个子命题的判断。
2. **结论骑墙**：没法给一句话干净的真假，只能给"部分可信"，说不清哪部分真、哪部分假。

### 拆分的本质

拆分就是把谣言"真与假交织"的缝线剪开，让真实的部分单独验、错误的部分单独验、夸大/偷换的部分单独验。这样真、假、夸大各归其位，谣言赖以存在的"以假乱真"的掩护就破了。

## 四、功能实现方式：一大段确定性逻辑 + 关键节点挂 LLM

整个产品的核心不是"AI 很聪明"，而是**每一步都有人管、有地方兜底**。拆开看，它是"确定性代码 + 几个关键节点上挂 LLM"。

**消息进入系统后的完整链路：**

1. **判命题类型**（确定性正则，见第五章）
2. **生成执行图 DAG**（`buildAdaptiveExecutionPlan()` 按类型拼节点和边，再拓扑排序决定谁先谁后、谁可并行）
3. **裁剪每个 Agent 的输入**（`buildAgentInput()`，每个 Agent 只收到它职责所需的材料，不塞全量）
4. **LLM 只做命题性判断，分数和边界由公式算**（见第六章）
5. **报告收束前过一道证据边界闸门**（见第七章）

**模型真正做事的节点：**

- RumorDetector：拆原子命题、识别谣言特征（需要语义理解）
- FactChecker：判断哪些是支持、哪些是反驳、哪些未解决
- SourceValidator：评估来源可靠性与可追溯性
- ReportComposer：合成报告

**模型不做的事：**

- 判类型（正则）
- 排序（拓扑）
- 打分（公式）
- 划边界（契约）

**为什么这么分层：** 模型擅长模糊判断，不擅长核算和边界。核算交给公式，边界交给契约。拆开之后，输出可复现、可审查、可兜底。

## 五、命题类型判断：目前是固定规则

### 当前实现

第一步判断命题类型，目前**不是模型做的，是几行正则（固定规则）**：

```typescript
function detectClaimType(claim: string): ExecutionDagClaimType {
  if (/(什么是|定义|概念|如何理解|是什么意思)/.test(claim)) return "concept";
  if (/(导致|造成|引发|因为|由于|归因|致癌|会让|使得|影响)/.test(claim)) return "causal";
  if (/(网传|称|据说|爆料|发生|发布|宣布|报道)/.test(claim)) return "event";
  return "mixed";
}
```

**正则是"按规则找字"的写法**，不读语义，只认字面。跑一万次结果一样。

### 为什么用正则

确定、可复现、零成本、零幻觉。在"先把流程跑通"的阶段，确定性比聪明更重要。

### 它的局限（必须诚实承认）

1. **不懂语义，只认词面**：会被"字面没命中但实际是同类"的句子骗过，也会被"字面命中但其实是另一回事"的句子误判。
2. **顺序是硬编码的**：先查概念、再查因果、再查事件，存在优先级 bug 隐患。
3. **用关键词代替了"判断"**：一个真正要判类型的系统应读懂句意，而不是"看到'导致'就喊因果"。

**结论：它是占位符，不是终局方案。** 正确做法是让 Planner（或 RumorDetector）用模型读语义判类型，还能对"一句话里多个子断言"分别路由。DAG 里的 `planner` 节点本想做这件事，但目前被跳过了（实际起作用的还是正则）。

## 六、可信度评分：公式算的，不是模型拍的

最终 0-100 的可信度分数，不是模型算的，是 `credibilityScore.ts` 里一个确定性公式，把五类信号加权聚合：

| 分量 | 来源 | 作用 |
| --- | --- | --- |
| 事实核查信号 | FactChecker | 判断核心事实是否成立 |
| 搜索证据信号 | 外部搜索 | 检查外部证据方向和质量 |
| 信源可靠性 | SourceValidator | 评估来源可信度 |
| 谣言严重度惩罚 | RumorDetector | 识别情绪煽动、匿名信源、绝对化表述等风险 |
| 缺失来源惩罚 | SourceValidator | 处理关键证据缺口 |

分档：80-100 高度可信 / 60-79 基本可信 / 40-59 存疑 / 20-39 低可信 / 0-19 高度可疑。

模型给方向，公式给分数，这样分数可复现、可解释、可追责。

## 七、证据边界：can say / cannot say

ReportComposer 的 prompt 里写死一条规则：**只能基于前序 Agent 已经输出的内容和搜索摘要，不能自己"想起"任何事实。** 它必须输出 `canSay`（证据允许说的）和 `cannotSay`（证据不允许说的）两个列表。

例子（"隔夜菜致癌"）：它只能说"正常储存下含量远低于安全限量"，而"不能说危险"——因为没找到实测数据。

正是这种"知道自己不能说什么"的克制，构成核查产品的信任来源。

## 八、失败的兜底

失败是 Agent 产品的常态，不是异常。设计原则是**失败要显式化，但不能让用户看到裸奔**。

1. **失败显式化**：搜索失败、模型超时、来源不可达，都显示为状态，而不是补写解释糊弄过去。
2. **可继续策略**：声明哪些是"可选/并行 Agent"（替代解释、反证评分），它们失败可继续走主线不阻断收束；核心 Agent 失败则阻断。
3. **确定性兜底**：ReportComposer 超时走确定性 fallback 公式，保证用户至少拿到结构完整的报告，不撒谎、不空白、不无限 loading。

## 九、多 Agent 的成本控制

- **输入瘦身**：每个 Agent 只收到职责所需的裁剪材料，token 上限不同。
- **共享材料**：搜索作为共享材料只准备一次，注入下游，不重复发起（`ensureSearch()`）。
- **成熟度分级**：不同 Agent 配置不同 reasoning effort，不平均烧。
