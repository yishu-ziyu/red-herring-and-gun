# ADR-007: CaseFile 脊柱 — 事件溯源的案件状态、代码裁判、有边界的追索 Agent

## 日期

2026-09-03

## 状态

已批准，实施中。路线：新包重建脊柱，域模块原样搬（见第「实施」节）。
与 ADR-001 ～ 006 冲突处以本文为准；它们保留为历史记录。

## 背景

黑客松版本证明了产品方向（拆命题、逐条判、绑来源、敢说查不清），但脊柱是累出来的：

- 两个执行引擎并存（固定管线默认、pi 循环 flag），哪个都不完整，切换从未有 golden 级证据。
- 报告是 `Record<string, unknown>`，被十来个函数顺序原地改写，用下划线字段打补丁；步骤之间靠数组下标和 agentId 约定传数据。
- 过程界面靠匹配工具名字符串推断，画的是管线的影子，不是案件。
- 判决由模型直接给出 true/false，代码事后打补丁（mixed guard、tiny bound）。
- eval 26 例 verdictAccuracy 0.69，失败集中在因果与半真半假——恰是逐条判决该赢的地方。
- 产品要延展为可追问的案件线程，现有状态模型撑不住多轮。

## 决策

### 1. 一份状态：案件是事件日志的折叠

`Case = reduce(events)`。`CaseEvent` 是封闭的类型联合；`reduce` 是纯函数；服务端、前端、测试、回放用同一个 reducer。

- SSE 传的是事件，不是「结果」。前端不再推断过程，只折叠事件。
- 审计轨迹就是事件日志本身，不另建 trace。
- 追问是往同一日志追加事件，不是新开一案。

为什么：这个产品的差异点是可审计。事件溯源让「为什么判成这样」有唯一答案：把日志放一遍。

### 2. 模型读，代码判

LLM 只出现在五个语义点，每处一张窄 schema 工单：

| 工单 | 只许回答 |
|---|---|
| 拆题 | 原句在断言什么：命题、类型、可否核查、在原句中的位置 |
| 自证 | 每条命题原句是否说过 |
| 立场判读 | 这篇证据对这条命题是支持 / 反驳 / 部分支持 / 只是相关，引出原文哪一句 |
| 追索决策 | 下一步追哪个缺口或 pivot、为什么；这页在引用谁 |
| 撰写 / 路由 | 用给定的命题判决和证据写直接回答；把追问归类 |

**真 / 假由 `judge()` 纯规则推出**：输入是立场记录 + 来源层级 + 来源独立性，输出是命题判决和依据。模型从不对命题说 true/false，只说每篇文档说了什么。引文必须是证据原文的子串，代码校验。

为什么：判决可复现、可单测、可解释成一句人话（「两个独立官方来源反驳，无支持」）。模型的幻觉被限制在「读错一篇文档」，而不是「编一个结论」。

### 3. 追索 Agent 有边界，是核心里唯一的循环

`Investigator` 负责「下一步去哪找证据」——这是核查问题里唯一开放式的决策。

- 感知：未解决命题的证据缺口 + frontier（候选下一跳）。
- 两个 frontier 生成器：
  - 缺口驱动查询：缺官方口径 / 原始来源 / 反证 / 时间锚 / 当事方 → 查询。
  - **pivot 驱动种子**：从已抓取的证据页抽取外链、被引机构与人、文号、日期、图片 → 新种子。这是 Maigret 式的实体空间递归，是「这句话从哪来」的真实动作。
- 决策：模型提议一个动作并说明理由；代码校验预算、去重、深度；提议无效则代码按预期价值选。
- 行动：`web_search` / `web_fetch` / `reverse_image` / `memory_recall`，全部有 schema。
- 判停：预算、连续零增益、全部命题已有一手依据、时间。增益定义为「给未解决命题带来新的独立来源簇」。
- 每一步是一条事件：目标、缺口、动作、理由、结果、增益。

产出写回案件：新证据（带 provenance：由哪次查询或哪个 pivot 得到）、引用边 `evidence.cites`（出处图）、未消费的 frontier。

为什么不是自治整案 Agent：拆题、判决、撰写的下一步都可枚举，写成代码是白拿；只有找证据不可枚举。为什么不引外部 Agent 框架：循环本身约两百行，工具四个；审计要求每一步可解释。

### 4. 冲突才辩论，裁判仍是代码

命题判决为 `contested`（支持与反驳都有够重的来源）时，起两个 `Investigator` 实例：控方只准找反证与原始来源，辩方只准找佐证与原语境，各有独立小预算，尽量用不同厂商的模型。两方产出的仍是立场记录（标 `by: prosecutor | defender`），`judge()` 用同一套规则重判。仍冲突则报告如实写「两边都有据」，可信度扣分。

为什么：辩论的收益来自信息不对称，不来自两个同款模型对同一份证据聊天。

### 5. 案件即线程

用户的每条消息经路由归类：`new_claim`（拆入同案）/ `pursue_frontier`（点了下一跳）/ `ask_case`（问案情）/ `challenge`（拿证据来质疑）/ `off_topic`（婉拒）。`ask_case` 只能从案件状态作答，代码校验回答不含案外 URL、不引入新事实；答不上就给出可追的 frontier。

### 6. 唯一收束闸

`finalize()` 是报告出门的唯一出口：结论第一句直接回答原句；每个 `[n]` 可解析到案内证据；含真 / 假判断的句子必须带引用；不出现工具名、厂商名、模型名、内部类型词；可信度由公式算并附分解。校验不过先修复，修不了给确定性兜底报告，不空白、不撒谎。

### 7. 实施：新包重建脊柱，域模块原样搬

```text
packages/core    纯域：casefile（事件、reducer、类型、不变量）、stages、investigator、judge、finalize、
                 搬入的域模块（拆题与自证、检索矩阵与证据追索策略、公式分、审稿规则、公开文案、LLM 多厂商路由）
packages/server  Express + SSE + 案件存储 + 配额；薄
packages/web     React；从 core 引 reducer；渲染案件，不渲染管线
packages/eval    golden + 指标 + 门禁
mvp/             参照；eval 打平后删除
```

不用 pi / LangGraph / DeepAgents。搬入的模块连同测试一起搬，不在搬的时候重写。

## 目标形状

```text
用户消息
  → 路由（一张工单）
  → 阶段流水（代码定顺序、时间预算、失败开放）
      拆题 → 自证 → 首轮检索 → 立场判读 → judge()
      → Investigator（有缺口才跑）→ 立场判读（增量）→ judge()
      → 交叉复核（contested 才跑）→ judge()
      → 撰写 → finalize()
  → 每一步是事件 → 日志 / SSE / 前端 reducer
```

## 不做

- 让模型给出 true/false 或分数。
- 整案交给模型决定路径。
- 给评委看的 Agent 运维台；界面只画案件（回答、命题、证据、出处图、下一跳）。
- 与案件无关的闲聊。
- 在搬迁时「顺手」重写域模块。

## 系统级验收

1. `packages/eval` 跑同一 golden 集，四项指标不低于 `mvp/server/eval/baseline.json`；之后 verdictAccuracy 目标 ≥ 0.85（目标，不是门禁）。
2. 新指标：grounding rate（true/false 判决有 A 级或 ≥2 独立簇依据的比例）、quote fidelity（引文为原文子串的比例）、出处链深度、p50/p95 延迟。
3. 回放确定性：任意案件 `reduce(log)` 与存储状态相等。
4. 公开事件流不含厂商 / 模型 / 工具名（测试）。
5. 三个 golden 案例在真实浏览器端到端走通：贴入 → 命题出现 → 证据流入 → 判决翻转 → 结论带可点引用 → 追问一次；桌面与 375px 截图。

## 后果

- 立场判读是新 schema，拆题与撰写工单需改写；这是有意的。
- `web_fetch` 成为常规动作，延迟预算必须显式：命题 ≤10s 可见，首批证据 ≤20s，临时判决 ≤40s，收束 ≤120s。
- 前端不再需要 streamAdapter 一类推断层。
- 旧 ADR 中的 pursuitHops、consensus debate、tiny bound 等概念不再保留；对应能力由事件日志、交叉复核、judge 规则承担。
