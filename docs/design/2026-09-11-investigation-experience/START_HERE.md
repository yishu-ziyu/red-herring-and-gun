# 交给 Codex 的启动指令

请在 yishu-ziyu/red-herring-and-gun 仓库实施本包的产品重构方案。

先阅读 IMPLEMENTATION_PLAN.md、ISSUES.md、ACCEPTANCE.md，打开 prototype.html 看首页、调查中、结果、来源、争议、历史、设置和手机；它们是设计提议，不是已发布产品。基线为 632746e25c551918f2ea72192b1e7de1bb5a9490，但必须从当前工作树开始，保留我的未提交改动与后续提交，不得重置到基线。

本次授权是对现有设计重新判断。仓库过去的产品规范和“契约”不作为审美与信息架构禁区；但现有数据、权限、引用真实性、额度和用户内容保护不能被顺手删掉。先用代码确认生产入口，不要只改 packages/web 或另建一个不接生产的 demo。

总体取舍：重做展示层与页面体验，保留核查内核；人物回来但不恢复满屏工程控制台；新增事实驱动的公共活动层，不直播内部思考；补齐停止、刷新恢复、历史和显式分享。不要借机换框架、上微服务或重写全部 Agent。

执行顺序按 PR-A → PR-B → PR-C → PR-D → PR-E → PR-F。第一阶段先补权限与提交静默失败测试；第二阶段给我可点击的真实组件预览与截图。需要我确认的是视觉提议，而不是一份抽象 PRD；无需等我来指挥普通实现细节。

每个阶段做完就运行对应测试、截桌面和手机，报告实际结果。涉及搜索/模型而环境无权限时，明确标注“未验证”，用可重复 fixture 覆盖 UI，不能冒充真实核查。任何新旧测试冲突，先区分旧视觉约束与真实正确性保障，不准简单删测试让构建变绿。

公共案例必须有真实来源和公开许可；本包的“海岬市公园”是虚构交互数据，不能改名“真实案例”上线。不要复制上一张概念图的阅读量、来源和医疗结论。

创建一个工作分支，例如 feat/investigation-experience；发现同名分支先检查，不覆盖。将 ISSUES.md 的任务作为工作清单；它们尚未创建到 GitHub，没有真实 Issue 编号。只有在我授权创建 GitHub Issues 后才创建对应主/子任务。当前可以直接按本地清单施工。

完成时给出：生产改动路径、逐项验收结果、预览地址、同尺寸截图、真实/模拟测试边界、旧数据兼容结果、未完成风险、回滚方法。不要自动合并、部署、更改域名、花费新的付费 API 额度或删除生产数据。
