# 2026-09-05 · 工单模型备用链覆盖已配置供应商

一句话：已配置的模型不能只出现在环境变量里；前序供应商失败后，工单必须继续尝试仍可用的候选，并把每次尝试留在运行证据中。

## Change

- 没有工单级显式覆盖时，候选表从本次运行实际配置的供应商与模型名生成。
- MiniMax、StepFun 失败后，只要 DeepSeek 或 MiMo 已配置且仍在时限内，就继续尝试，而不是提前结束工单。
- 每次尝试保留供应商、模型、成功与否、延迟和错误类别；不得记录密钥。
- 工单级显式覆盖仍表示只使用调用者明确给出的候选表，不能被默认链暗中扩充。

## Not this

- 为某条评估原句写特判。
- 把没有密钥或没有配置模型名的供应商塞进真实候选链。
- 用无限重试掩盖供应商故障。
- 因为备用链补全，就声称拆解、搜索或判词质量已经改善。

## Evaluator

- 单元测试：传入四组供应商凭据和四个不同模型名时，默认候选包含四组实际模型名；只配置两组时不调用另外两组。
- 单元测试：前两个候选返回内容审查或无正文后，第三个已配置候选被尝试并可完成工单；attempts 保留前两次原始失败类别。
- 单元测试：`RHG_MODEL_<JOB>` 存在时，候选严格等于显式列表。
- 聚焦回归：`packages/core` 的 `jobModels` 与 `callJob` 测试通过。
- 真实运行检查：若工单失败，运行记录中的候选尝试数必须等于截止期限内所有合格候选；仍有合格候选未尝试则判失败。

## Goal / Hard bar / Improve

- Goal：供应商单点失败不再直接变成产品无判断。
- Hard bar：候选来源真实、后续候选确实被调用、尝试证据完整、无密钥泄漏。
- Improve：根据各工单的成功率与延迟重新排序候选；这是有运行数据后的后续决策，不属于本次修改。
