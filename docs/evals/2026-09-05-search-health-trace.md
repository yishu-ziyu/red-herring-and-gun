# 2026-09-05 · 搜索健康进入案件轨迹

一句话：评测必须知道每个已调用搜索源是成功、失败还是被取消，以及贡献了多少结果；没有这层观测时不得声称搜索正常。

## Change

- 每次查询对每个实际调用的搜索源记录开始与结束；结束至少区分成功、失败、取消，并保留结果数、耗时和安全错误类别。
- 搜索轨迹进入内部 `CaseEvent`，随评测 JSONL 保存；公开 SSE 继续清除供应商名、模型名和内部错误，不向用户泄露运维信息。
- 评测按真实轨迹给出 `healthy`、`degraded`、`empty`、`failed`、`unknown`：全部完成且有结果为 healthy；至少一家完成但部分来源失败为 degraded；所有来源正常完成但都没有结果为 empty；没有来源正常完成为 failed；缺少足够事件为 unknown。
- 对预期进入核查的案例，`unknown` 和 `failed` 使本次评测运行无效；预期提前停止的案例本来就不搜索，`unknown` 不使其无效。`degraded` 和 `empty` 可计算产品指标，但必须单列失败来源或空结果，不能汇总成正常。

## Not this

- 根据最终出现了 evidence 就反推所有搜索源健康。
- 把空结果等同于有可用结果。
- 把供应商原始报错、请求标识、密钥或内部 URL 发到公开流。
- 只改评测器的推断，不补生产搜索路径的可观测事件。

## Evaluator

- core 单元测试：两家成功且至少一家有结果时，内部事件能重建各来源结果数和 healthy。
- core 单元测试：一家成功有结果、另一家失败时为 degraded，并保留失败来源和安全错误类别。
- core 单元测试：全部失败、全部空结果、外部取消分别可区分；事件回放后信息不丢。
- eval 单元测试：缺搜索来源事件为 unknown；全部正常但零结果为 empty；预期进入核查时 unknown/failed 令 run `valid: false`；预期提前停止时 unknown 仍有效；degraded/empty 不伪装为 healthy。
- 隐私回归：公开事件转换后不含 provider、model、原始 error、request id 或密钥形状。
- 真实回归：单例运行 JSONL 中能看到实际调用来源的开始与结束，汇总值与逐条事件一致。

## Goal / Hard bar / Improve

- Goal：搜索配置或供应商故障能从产品逻辑失败中被独立识别。
- Hard bar：内部轨迹可重建、评测有效性受它约束、公开面不泄露内部信息。
- Improve：积累足够运行后，按工单和查询类型比较来源成功率、贡献率与延迟，再决定排序和套餐分配。
