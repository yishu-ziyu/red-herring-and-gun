# Token Plan 搜索接入

## Change

- 已配置 MiniMax Coding Plan 或 StepFun Step Plan 凭据时，服务端把套餐自带的网页搜索加入现有并行检索矩阵。
- 两路搜索返回的真实 URL、标题、摘要和时间信息进入统一证据结构，并保留各自 provider 归属。
- `packages/core` 主链路与仍在生产使用的 `mvp/` 链路行为一致；检索进度能区分 MiniMax、StepFun 和其他来源。
- 任一路超时、套餐额度耗尽或响应异常时，只标记该路失败，其余检索和最终收口继续。
- 复用现有服务端套餐凭据；不要求用户再申请一套搜索密钥。

## Not this

- 不是让聊天模型在提示词里自行声称“已经联网”。
- 不是浏览器直连供应商，也不把密钥、请求 ID 或原始诊断写进 SSE、报告或前端。
- 不是把供应商生成的回答当成事实；只有带真实 URL 的搜索结果能进入证据层。
- 不是用一个统称抹掉来源归属，也不是为通过测试伪造固定结果。

## Evaluator

- 自动：供应商请求契约和响应解析单测覆盖成功、空结果、异常、超时与额度失败；断言 provider provenance 和 URL 去重仍成立。
- 自动：默认 provider 发现与进度事件覆盖两家套餐搜索；缺少对应凭据时不得发起该路请求。
- 自动：公开事件中不得出现套餐凭据、Authorization、供应商请求 ID 或原始错误正文。
- 自动：`npm test`、`npm run build`、`cd mvp && npm test`。
- 协调者活测：用当前两家 Token Plan 各发起真实检索，核对真实 URL、可读摘要、供应商归属、失败隔离和可见进度；具体材料与判断阈值不交给实现者。

## 结果（2026-09-05）

- 自动：聚焦 46 项通过；根目录 646 项通过；`mvp` 839 项通过、1 项跳过；根目录与 `mvp` 构建通过。
- 活测：两家项目适配器各返回 8 条带 URL 的结果；统一证据层合并后 URL 去重与 provider provenance 正常。
- 生产镜像：真实检索事件同时显示 MiniMax Token Plan 与阶跃 Step Plan 完成；单路失败隔离由 stub 测试覆盖。
- 界面走查：设置页两路均位于「已预置」，没有第二套搜索密钥输入框，名称与套餐边界明确；最终视觉取舍仍由用户判断。
- 总体门禁：`eval-1788549137105` 已运行并退出 1；两家套餐检索在 run 中持续产出且没有 provider 失败记录，但旧可信度基线和资格闸分母仍使总体门禁不通过。这个结果不替代本页的搜索接入验收，也不允许 T20 上线切换。
