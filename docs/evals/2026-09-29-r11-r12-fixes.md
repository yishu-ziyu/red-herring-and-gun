# R11 / R12 修复验收（2026-09-29）

用户已批准修 `docs/rewrite-issues.md` 的 R11、R12，行为变更是有意的。R5 只看到「被提前拒绝的请求，额度结算后 remaining 恢复、used 不变」为止，不重做额度闸。

## 每个修法可能怎么坏（先列，再写代码）

R11（接回流与重复提交流公开清洗）
1. 清洗漏了一条写帧路径：`investigationEventsHandler` 有补发（run_started、activity、snapshot、run_state）和直播（订阅）两段，只改一段等于没修。重复提交走的是同一个处理器，但要单独验证。
2. 清洗丢了客户端接回要用的字段：`runId`、`caseId`、`status`、`terminal`、`investigation`、`activity` 的正文。`run_state` 帧被清洗后必须仍带 `terminal`，否则流永不关闭。
3. 清洗把 `error` 帧的 `checks_exhausted` / `byo_key_failed` 文案吞成通用文案（首次提交的流是保留的，接回流必须一致）。
4. 复制了一份清洗逻辑，日后两边漂移。只许复用 `toPublicStreamEvent`。
5. 清洗修改了总线上的原对象，影响其他订阅者（首次提交的流也在订阅）。`toPublicStreamEvent` 拷贝后处理，测试要确认两条流互不影响。

R12（早退 400 退还名额）
1. 退还调用两次给出多余名额：`releaseFreeCheck` 靠 `ticket.settled` 幂等，测试要连调两次看 `inflight` 不为负、remaining 不超过上限。
2. 对已经 commit 的请求再 release：三处 400 都在建 run 之前，不会出现；但测试要断言 400 后 used 仍为 0。
3. `req.checkTicket` 为空（额度未开启、MCP 路径、运维放行）时 release 空指针。要判空。
4. 只修了两处，漏掉 JSON 解析失败那处。三处都要测。
5. R5：请求的 `close` 事件晚于 400 返回时会调 `commitFreeCheck`；但 release 先把 `settled` 置真，之后补扣是空操作。要验证 400 后再触发 close，used 仍为 0。
6. 账号用户（kind=account）也走 release 分支，要覆盖账号 remaining 恢复。
