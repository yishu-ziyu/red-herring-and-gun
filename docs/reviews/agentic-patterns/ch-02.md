## 对能信/不能信的意义
该查的命题进检索和真假清单，立场句不订真假，半真半假才能分截判。
证据不够或两边打架时，代码决定再搜或换第二模型，结论才敢说能信、不能信、还查不清。
若拆题把一句能核对的流传说法标成立场，代码照标签跳过检索，用户会在该条只看到「立场型 / 不适用真/假判断」，等于没查却当成不适用。

## 缺口
类型闸没有复核。
MiniMax-M3 一次填对 `type` / `verifiable`，后面整条链照做。
把能核对的流传说法标成价值/规范后，该条不检索、不进 `subclaimVerdicts`，报告只写「立场型 / 不适用真/假判断」。
这是「能核对的说法没被查」。
说明书已记为已知不满，见 `docs/PRODUCT_SPEC.md` 第四节与第七节 2026-08-19 条、`mvp/docs/DEV-LOG.md` 2026-08-19 条。
未改代码。不要当成已经修好。

失败不对称。
拆题服务崩溃会走 `fallbackRumorStep`，整句当可核查继续搜。
模型自信标错反而跳过检索。
自信标错比服务崩溃更伤用户看见的结论。

类型闸在产品里几乎不可见。
用户只看见「立场型 / 不适用真/假判断」，看不见是拆题工单标的、也不知道没有第二意见。
连「谁来判断这些类型」都要猜，标错时无法从界面察觉漏查。

P2 案件类型分支未落地。
截图/数字/引语与纯文本走同一检索政策，可能少查原图或原始发布。
伤害小于类型标错漏查；不把本章做成 P2 施工单。

## 方案（仅 partial 或 missing-and-needed）
Goal:
给拆题标签补一闸，专门挡住「读起来像流传说法、却被标成立场」的漏查。
仍由代码决定搜不搜；模型只许再填一张类型工单，不许选下一条链。

Hard bar:
把一句能核对的流传事实（例如「某地要建地铁」「隔夜菜会致癌」）交给拆题，即使主拆题输出 `verifiable: false` / `type: value`，该条仍必须进入 `retrieveForAtoms` 的检索清单，报告不得只显示「立场型 / 不适用真/假判断」。
纯价值句（例如「政府应该禁止这件事」）仍不检索，报告仍是「立场型 / 不适用真/假判断」。
现有因果分支、evidenceLoop、crossExam 的触发条件不变。

改哪些文件:
优先在 `mvp/server/src/lib/claimAtom/` 加纯函数闸（可单测）：对 `verifiable === false` 的原子做「像不像可核对流传说法」判定。
像：强制改回可核查并检索；或只对这些争议条再叫一次类型工单（第二意见须与主拆题不同源，比照 `mvp/server/src/lib/crossExam/crossExam.ts` 的异源约束），分歧则搜。
接线：`mvp/server/src/lib/atomSearch.ts` 的 `retrieveForAtoms`、`mvp/server/src/lib/reportAssembly/assembleFinalReport.ts`、必要时 `mvp/server/src/lib/casePipeline/runCasePipeline.ts`。
工单若新增：只许输出 `type` / `verifiable`，复用 `mvp/server/src/lib/agentConfigs.ts` 的拆题枚举，不许写能信/不能信。
回归：`mvp/server/src/lib/claimAtom/` 与 `mvp/server/src/lib/atomSearch.retrieve.test.ts`、`mvp/server/src/lib/agentConfigs.test.ts`。
产品可见性：结果页该条旁写清「拆题标为立场型，已复核 / 已强制检索」，不要只丢一枚徽章。
拍板并落地后再改 `docs/PRODUCT_SPEC.md` 第四节与 `CONTEXT.md` type gate。
未拍板不改生产管线。

明确不做:
不让 LLM 自己选下一条链、不输出路由类别去调度子 Agent。
不迁 LangGraph / Google ADK / DeepAgents，不引入嵌入路由器。
不另雇更强模型当专职分类器；拆题默认仍是 MiniMax-M3 填工单。
不让 FactChecker / ReportComposer 回头改类型。
不把「还查不清」做成拆题标签。
不做无条件全量双模型拆题。
不把第八节 P2 截图/数字/引语策略塞进这一闸。
