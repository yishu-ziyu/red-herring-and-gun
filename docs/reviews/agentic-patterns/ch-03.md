## 书要解决什么
彼此不依赖的采集可以同时发出，不必排成一条队去等外部接口。
把各路材料收成一份判断，必须等采完再写。
目的是少空等、独立检查仍做完，不是让模型自己拆任务、自己开子智能体。

对应路径：`mvp/server/src/handlers.ts` 的 `callParallelSearchProviders` 对 360、AnySearch、Metaso、Tavily、Exa 同时发出，用 `Promise.allSettled` 收。
无 key 或失败记入缺口。
有一路成功就合并来源。
同一原子的 2–3 条 query 在 `retrieveAtomSources` 里再同时发出。
`mvp/server/src/lib/atomSearchQuery.ts` 的 `mergeParallelSearchPayloads` 先 RRF 再排序。
可核查原子层在 `mvp/server/src/lib/atomSearch.ts` 的 `retrieveForAtoms`，默认 `mode: "parallel"`，上限 6。
JSON 入口 `/api/agent/orchestrate`（`orchestrateHandler`）把 `searchMode` 设成 `"parallel"`。
SSE 入口 `/api/agent/orchestrate-stream`（`orchestrateStreamHandler`）把 `searchMode` 设成 `"sequential"`。
这只把原子与原子改成排队，让过程事件成对出现。
每个原子内部仍走多 query × 多源并行。
`mvp/server/src/lib/casePipeline/runCasePipeline.ts` Phase 2 同时跑 FactChecker 与 SourceValidator。
一路失败走兜底，检索到的 URL 仍能进报告。
拆出因果原子时，`alternative_explanation_searcher` 与 `counter_evidence_grader` 同样同时跑，失败不阻断收束。
必须串行的是拆题 → 自证 → 检索 → 核查 → 证据循环 → 写报告。
`mvp/server/src/lib/evidenceLoop/evidenceLoop.ts` 对目标和 query 按顺序等待，因为后一跳依赖前一跳的缺口。
补查串行见 `docs/adr/ADR-004-evidence-sufficiency-loop.md` 与 `docs/adr/ADR-005-evidence-pursuit-search-policy.md`。
被标成立场或价值的判断不发起检索，因此不进并行采集。

`docs/PRODUCT_SPEC.md` 第四节要求检索并行调用有 key 的源，失败不阻断整次。
独立采集并行、有依赖的综合串行，落在 Case Pipeline 的阶段切分上，不是落在图编排上。

## 对能信/不能信的意义
多路来源同时捞，一条源挂了不会把整句写成假，也不会没来源却写成能信。
半真半假的每一截各自去搜，搜完才对照写哪一截能信、哪一截不能信。
总判断必须等各截材料和来源评估到齐，过程流把原子排队只是让进度一条条看清，并不少查。
