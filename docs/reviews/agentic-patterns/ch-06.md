# 第 6 章 · 规划

## 裁决
partial

## 分数
4 / 5

## 书要解决什么
复杂目标不能一步做完，要先拆成可执行的顺序步骤，必要时根据新信息改下一步。
书把「怎么走」交给模型当场发明：先写一份计划，再按计划做，做不通就重写计划。
书自己也写了另一句：方法已经知道、可以重复时，应把智能体关进预先写好的固定工作流，不要开放式规划。

## 我们有没有
有但形状不同。
核查域下一步只有三种：继续查、换问法、停。
这三种写得进代码，不需要模型发现路径。
查询组合算计划，但是证据计划，不是步骤顺序计划。
对应路径：`mvp/server/src/lib/casePipeline/runCasePipeline.ts` 生产运行时是写死的 phase：拆题 → 自证 → 按原子检索 → 核查//信源 → 证据充分性循环 → 冲突才交叉复核 → 因果原子才加替代解释/反证评分 → 写报告 → 代码审稿。
`mvp/server/src/lib/evidencePursuit/evidencePursuit.ts` 的 `buildQueryPortfolio` 为每条可核查判断生成六路问法（exact / entity / primary / temporal / refutation / alternative）；`assessEvidenceGap` / `queriesForGap` 按还缺的槽位选下一问；`PursuitAction` 类型就是 `continue` | `switch` | `stop`。
`mvp/server/src/lib/atomSearchQuery.ts` 的 `buildAtomSearchQueries` 从组合里实搜 2–3 路；有日期或数字才开第三路；`mergeParallelSearchPayloads` 用 RRF 融合多问结果。
`mvp/server/src/lib/evidenceLoop/evidenceLoop.ts` 的 `planRoundQueries` / `runEvidenceLoop`：未证实或两边打架才补查；模型只改写检索词，失败回退 `fallbackRewriteQueries`；增益不够则换策略再问，够了或笼子用尽则停。
`runCasePipeline.ts` 把 hops 写入 `finalReport.evidencePursuit`，用户回看的是「还缺什么 → 换问法 → 命中/仍未命中」，不是一份开放式研究提纲。
依据：`docs/PRODUCT_SPEC.md` 第四节 4a、第六节、第八节「行动空间可枚举」；`docs/adr/ADR-003-production-case-pipeline.md`、`docs/adr/ADR-004-evidence-sufficiency-loop.md`、`docs/adr/ADR-005-evidence-pursuit-search-policy.md`。
故意不做：书里的 CrewAI「先规划再写摘要」、Google / OpenAI Deep Research 那种模型自己拆子问题并改路径、让用户先批一份研究计划再自治浏览。
`mvp/src/lib/agentRuntime/AgentRuntime.ts` 的 `buildAdaptiveExecutionPlan` / `executeDag` 仍按正则猜 concept / causal / event / mixed 画 DAG，只给 eval / 本地 dev 用，生产不跑。
依据：`docs/adr/ADR-001-agent-architecture-upgrade.md` 已被 ADR-003 收编；`docs/PRODUCT_SPEC.md` 第六节「不是自治 Agent」「动态加在证据维度，不加在拓扑维度」；`docs/adr/ADR-002-deepagents-evaluation.md` 不迁 LangGraph / DeepAgents。
书里哪句不要跟着走：「计划并非预先设定，而是根据请求动态生成」——那句针对方法未知的任务；核查的方法已知。
书里哪句要跟着走：「方法需要被发现，还是已经已知？」——本域已经已知，固定工作流不是欠债。

## 对能信/不能信的意义
用户丢进一句话，系统不是当场发明一条新路线，而是按同一套步骤查，查不够就换问法，仍不够就说「还查不清」。
同一说法今天能信、明天不能信，差的应是搜到的材料，不应是模型改了步骤顺序。
查询组合让「找原始发布 / 找反证 / 对时间」成为可见的下一跳，用户回看过程时能对上结论是怎么来的。

## 缺口
P2 案件类型分支未落地。
三种材料仍多半走同一套文字问法，能核对的出处会漏。
截图：`mvp/server/src/handlers.ts` 的 `callStepFunVisionForIntake` / `composeClaimWithVision` 只做 OCR 和抽句，然后把图忘掉，改走文字管线。
没有以图搜图，没有查原图首发。
旧图新配文、截图断章、P 图，可能被当成「文字说法还查不清」，图本身的出处从未被追。
统计数字：`buildAtomSearchQueries` 见到数字或日期会多开一路，`primary` 的文案是「官方通报 发布 原文」。
这是通用后缀，不是「这条数字的原始公报 / 记者会 / 统计表」。
转载通稿可能被写成能信。
引语：`quotedSpan` 只把引号内字面做成 exact 查询，没有「说话人 + 场合 + 前后文」的原语境策略。
断章可能搜到复述，看不到被砍掉的上下文。
步骤顺序上唯一按类型加步的是因果：`runCasePipeline.ts` 见到 `claimAtomTypes` 含 `causal` 才跑替代解释与反证评分。
截图 / 数字 / 引语没有对应的证据策略。
`ClaimAtomType`（`mvp/server/src/lib/claimAtom/types.ts`）没有截图、统计、引语这几档。
拆题工单标不出这类，代码也就无法按类选问法。
`PursuitAction` 虽有 `switch`，hops 实际只记 `continue` / `stop`。
换问法发生在下一轮 `purpose` 变化里，用户过程层不容易看成「换问法」。
ADR-004 写明 P2 不在该决策范围，另立。
说明书第八节仍把 P2 列为「至少 3 类谣言 20%」的兑现项。
该追原图或原始发布的案子，会被收成「还查不清」，或绑上二手转载的「能信」。

## 方案（仅 partial 或 missing-and-needed）
Goal:
在现有 Case Pipeline 里补三类证据策略（截图追原图、数字追原始发布、引语追原语境），下一步仍只有继续查 / 换问法 / 停，由代码选。
Hard bar:
丢进一张更早出现过、配了新标题的截图：报告能点到更早出处，或明确写「原图出处未查到」，不得把 OCR 文字搜到的二手帖当成这张图的来源。
丢进一条带具体数字的统计传闻：至少有一路查询指向公报 / 记者会 / 原始数据表；报告要么绑上原始发布，要么写「未能证实原始发布」，不得把同通稿转载写成能信。
丢进一句带引号的断章：至少有一路查询带说话人与原语境；报告能指出前后文缺失，或绑上可点开的原始发布。
改哪些文件:
`mvp/server/src/lib/evidencePursuit/evidencePursuit.ts`：为 image-origin / stat-primary / quote-context 增加 purpose 与缺口槽位；数字抽出数字串，引语抽出说话人+引号句。
`mvp/server/src/lib/atomSearchQuery.ts`：首轮按案件形态从组合里选路，而不是三类共用 exact+辟谣。
`mvp/server/src/lib/evidenceLoop/evidenceLoop.ts`：换策略时 hops 的 `action` 写成 `switch`；截图补查优先原图/首发，数字补查优先原始发布，引语补查优先原语境。
`mvp/server/src/handlers.ts`：Vision 之后不要丢掉图片字节；把 `ocrTexts` / `sourceHints` 与「需要原图检索」标记交给检索缝，而不是只拼进 claim 字符串。
若要接以图搜图：新增小模块（检索适配，不是新 Agent），由 `searchOne` 旁路调用；失败显式进缺口，不编来源。
`mvp/server/src/lib/casePipeline/runCasePipeline.ts`：只编排，不改 phase 拓扑；因果那两步保持现有条件触发。
明确不做:
不恢复 ADR-001 的生产 DAG，不让 `buildAdaptiveExecutionPlan` 接管 Case Pipeline。
不让模型选择下一步，不引入 CrewAI / Deep Research 式开放计划，不迁 LangGraph。
不新开平行 Search Agent，不把动态加回拓扑维度。
