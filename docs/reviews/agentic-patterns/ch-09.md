## 书要解决什么
智能体要用经验改下一次怎么做，不能每次面对同类情况都像第一次。
书给的手段是强化学习、微调（PPO / DPO）、在线改权重，以及改自己的代码（SICA / AlphaEvolve）。
书也列了「基于记忆的学习」：把成功问法和失败缺口存下来，下次先参考。

## 我们有没有
有但形状不同。
微调、在线强化学习、自己改自己的代码：故意不做。
依据：`docs/PRODUCT_SPEC.md` 第八节「模型后训练 ➖ 不做」；`docs/adr/ADR-001-agent-architecture-upgrade.md` 不换 API 模型、不另训权重；`docs/adr/ADR-005-evidence-pursuit-search-policy.md`「不做 Search-R1 / 强化学习搜策」。
结案会写记忆。
`mvp/server/src/lib/casePipeline/runCasePipeline.ts` Phase 3c 调 `buildMemoryCandidatesFromRun`，有 store 就 `propose`。
候选种类在 `mvp/server/src/lib/memoryCandidateGenerator.ts`：案例边界、有效查询、来源域名、未解缺口、半真半假结构。
浏览器结案后把本案写入本地案件库：`mvp/src/lib/knowledgeBase.ts` 的 `saveCase`；`mvp/src/components/v3/phases/MissionControlView.tsx` 调用。
下一案开始前，浏览器用 `semanticClaimSimilarity`（`mvp/src/lib/semanticRecall.ts`，服务端副本在 `mvp/server/src/lib/semanticRecall.ts`）找相似旧案，经 `mvp/server/src/handlers.ts` 的 `normalizeClientMemoryRecall` 塞进每个 Agent 的 `memoryRecall`。
政策写死：旧案只作线索，不得当本案证据。
`mvp/server/src/lib/agentConfigs.ts` 里 FactChecker 写「模型记忆不是核查」，只许看本次 `search360` / `atomSearches`。
拆题工单不提 `memoryRecall`。
检索代码不读记忆：`mvp/server/src/lib/atomSearchQuery.ts` 没有上次 query、没有来源域名、没有缺口。
`knowledgeBase.getSearchStrategy` / `updateSearchStrategy` 在仓库里没有调用方。
`memoryCandidateStore.searchAccepted` 只在非生产的 `mvp/src/lib/agentRuntime/AgentRuntime.ts` 里用；生产 `runCasePipeline` 开案时不召回。
依据：`docs/adr/ADR-003-production-case-pipeline.md`，AgentRuntime 不是生产真相。
候选默认 `proposed`。
界面文案写「确认后才参与新案召回」。
单案里 `evidenceLoop` 会换问法，那是这一案补查，不是跨案学习。
`mvp/server/eval/` 是对照 golden 打分、相对 `eval/baseline.json` 卡门禁，追加 `.ship/evaluation/benchmark-history.jsonl`。
`eval/runCase.ts` 不传 `memoryRecall`，也不挂 `memoryCandidateStore`。
失败进 `eval/score.ts` 的 `failures` 列表，不改下一案的拆题、query 或检索预算。
`expectsEvidenceLoop` 只观测补查有没有触发、有没有翻案，不写回策略。
eval 是量尺，不是从失败学习。

## 对能信/不能信的意义
同一句谣第二次进来，用户仍要等完整检索。
旧案不会让系统少搜，也不会先走上次打中的问法。
旧案结论被挡住不当证据，这是对的：否则会没有本案来源却写成能信或不能信。
拆题类型闸标错后，下一案同类说法仍可能再标成「立场型 / 不适用真/假判断」而不去查。
记忆没有把这次标错写回拆题。

## 缺口
同类谣第二次仍从零搜。
`retrieveForAtoms` 不读上次有效 query、来源域名、证据缺口。
记忆主要落在浏览器 localStorage。
换设备或清掉本地库，生产管线自己不会召回服务器上的 `.agent-memory/candidates.jsonl`。
候选要人手确认才当「已接受」。
自动入库的是案件摘要，只进提示词，不进检索。
`eval/` 失败不会让下一案查得更快或更准。
它只告诉人哪条 golden 没过。
拆题标错没有从失败回写。
同一类能核对的说法可能再次被标成「立场型 / 不适用真/假判断」而不去查。

## 方案（仅 partial 或 missing-and-needed）
Goal:
同类说法第二次检索先复用上次有效问法和未解缺口。
结论仍只绑本案新检索到的 URL。
Hard bar:
同一句或同义改写（电瓶车 ↔ 电动车）再查。
首轮实搜 query 含上次 `effectiveQueries` 或 `evidenceGaps` 中至少一条。
报告 `supportingSources` 的 URL 必须出现在本案 `atomSearchBundle` 里。
不得出现仅来自旧案、本案未检索的 URL。
改哪些文件:
`mvp/server/src/lib/casePipeline/runCasePipeline.ts`：Phase 1b 之前用 `memoryCandidateStore.searchAccepted` 取出 query / 缺口线索。
`mvp/server/src/lib/atomSearchQuery.ts`：把召回的有效 query / 缺口并进 portfolio，预算仍封顶。
`mvp/server/src/handlers.ts`：服务端召回，不依赖浏览器是否带了 `memoryRecall`。
`mvp/server/eval/runCase.ts`：第二次同义改写时断言 query 复用（观测，不把门禁绑在「更快」上）。
明确不做:
不微调、不 PPO、不 DPO、不在线改权重。
不让智能体改自己的代码（SICA / AlphaEvolve）。
不把旧案 `verdict` / `credibilityScore` 写成能信或不能信。
不因旧案相似就跳过检索。
不自动把 `proposed` 候选的判词当成已接受。
可自动复用的只限 query 字符串和缺口，不含判词。
