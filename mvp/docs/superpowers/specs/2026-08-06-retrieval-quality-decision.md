## 1. 问题

目标（产品）：证据链里少出现「不能当证据的噪声」。

约束：

- 我们是 **多搜索 API 聚合方**，不做全网爬虫与 PageRank 级链接图。
- 已有：按可核查原子召回、多源并行、无 URL 丢弃、域名粗标、判定层 SourceValidator。
- 缺口：检索后几乎没有 **标准意义上的筛选漏斗**（过滤 → 排序 → 截断）；噪声大量原样进 FactChecker。

标准做法骨架（IR）：

```text
宽召回 → 硬过滤 → 排序/精排 → 截断 top-K → 再给下游
```

我们今天只到「宽召回 + 极弱过滤」。

---

## 2. 我的判断（主张，不是菜单）

### 2.1 本轮要达成的目标（可验收）

**不是**「检索保证权威」。  
**是**：「进入 FactChecker 的每条原子证据列表，以可追溯、去重、有限条数为默认，明显废料尽量进不了前排。」

用户可感知（弱但真实）：

- 同一转载站群不会刷出十几条「独立证据」。
- 没有 URL / 空壳结果不会当证据出现。
- 每条原子最多看到有限条来源（例如 5），且优先更像可用的。

### 2.2 本轮明确不做

| 不做 | 理由 |
|------|------|
| 再接新搜索 API | 多召回不解筛选；先修漏斗 |
| 自建 spam ML / TrustRank / 全网链接图 | 成本与数据都不够；超出 API 聚合定位 |
| 用大模型对每条结果精排（重） | 延迟与费用高；本轮先确定性规则 |
| 垂直领域完整白名单（医疗/法律全集） | 维护成本高；可作后续配置，不作本轮阻塞 |
| 把 SourceValidator 当检索筛选的替代并停止改进检索层 | 判定层该留；但垃圾应在进模型前就少 |

### 2.3 本轮要做的方案（我选定的组合）

**一轮交付：筛选漏斗 v1（确定性，可测）**

插在：`buildAtomSearchBundle` 之前或之内——各源结果合并之后、注入 FactChecker 之前。

```text
各源召回（已有）
  → [S1] 硬过滤
  → [S2] 跨源去重
  → [S3] 轻量打分 + 截断 top-K（每原子）
  → 再给 FactChecker / 报告绑证据
```

#### S1 硬过滤（必须）

丢弃：

1. 无 `http/https` URL  
2. URL 无法 parse  
3. 标题与摘要皆空  
4. 可选配置的 **denylist 域名后缀/主机**（内置一小份默认：明显短链/追踪站可后续扩；本轮至少支持配置钩子 + 3～5 个示例）

保留但降权（不丢）：常见 UGC/自媒体域（已有启发式「低」）——**本轮不因「低」直接删除**，避免误杀线索。

#### S2 跨源去重（必须）

键优先级：

1. 规范化 URL（去 fragment、统一 host 小写、去常见追踪参数 `utm_*`）  
2. 若无稳定 URL：`(注册域名 + 标题规范化)`  

同一键只留一条：优先保留 **可信度标签更高** 的，其次摘要更长的。

#### S3 轻量打分 + 截断（必须）

每条来源确定性分数（0–100 量级即可），因子仅用已有字段：

| 因子 | 方向 |
|------|------|
| 域名启发式 高/中/低/未知 | 高 > 中 > 未知 > 低 |
| 摘要非空且长度 | 过短惩罚 |
| 标题非空 | 空惩罚 |

**不做** query–文档语义相关模型（本轮）。  
相关度暂时 **信任提供方排序 + 我们的可用度分** 混合：  
`score = 0.6 * provider_rank_score + 0.4 * usability_score`  
（provider_rank：源内原次序映射为分；无次序则只用 usability。）

每原子截断：**K = 5**（写入常量，可配置 env 覆盖）。

### 2.4 为什么选这套，不选别的

| 备选 | 我的否决/推迟理由 |
|------|-------------------|
| 只加白名单医学域 | 产品不止医疗；白名单过早会召回塌缩 |
| 只靠 SourceValidator | 垃圾已进 LLM 上下文，贵且不稳；应前移 |
| 立刻上 cross-encoder rerank | 对，但是 v2；先要有干净输入与评测钩子 |
| 再多接两家搜索 | 与目标相反 |

**顺序判断：**  
先 S1+S2+S3（筛选），再考虑 v2 rerank 或垂直白名单。  
与「先判断再改再验收」一致：本文件是判断；确认后才改。

## 3. 验收（怎样算改对了）

### 3.1 自动化（合并门槛）

| ID | When | Then |
|----|------|------|
| A1 | 同一规范化 URL 出现在两个 provider 结果 | 合并后只 1 条 |
| A2 | 条目无 URL 或非 http(s) | 不出现在 bundle.sources / byAtom |
| A3 | 单原子合并后 >5 条可用源 | 交给 FactChecker 的该原子 sources ≤ 5 |
| A4 | 标题摘要皆空 | 被过滤 |
| A5 | 现有 atomSearch / handlers 相关单测 | 全绿；新增 S1–S3 纯函数单测 |

### 3.2 手工/半手工（你或 Agent 跑一次）

固定 query（沿用）：`隔夜菜致癌 科学证据` 拆出的某一可核查原子。

| ID | Then |
|----|------|
| H1 | 日志或 debug 字段能看到：过滤前条数 → 过滤后条数 → 截断后条数 |
| H2 | 报告/ atomSearches 中无「无 URL」项 |
| H3 | 目测：同一转载 URL 不重复刷屏 |

### 3.3 明确不验收

- 医学结论是否正确  
- spam 率降到大厂水平  
- AnySearch 条数变多

## 4. 实现边界（已落地）

| 项 | 约定 |
|----|------|
| 主改文件 | `mvp/server/src/lib/retrievalFilter.ts`（纯函数）；`atomSearch.ts` 在 `buildAtomSearchBundle` 内接线 |
| 不改 | FactChecker prompt 大改、新 provider、前端大改 |
| 可观测性 | bundle.`filterMeta: { perAtom, totals: { before, afterFilter, afterDedupe, afterTopK } }`；`aggregate.traceText` 含筛选前后条数 |
| 风险 | 过滤过狠 → 证据变少 → unverified 增多；用「低域降权不删除」缓解 |

## 7. 一句话决策

**在原子多源召回之后，加确定性筛选漏斗 v1：硬过滤 → 跨源去重 → 可用度打分截断 top-5；不接新 API、不上重型精排；用单测 + 条数/去重可观察结果验收。**
